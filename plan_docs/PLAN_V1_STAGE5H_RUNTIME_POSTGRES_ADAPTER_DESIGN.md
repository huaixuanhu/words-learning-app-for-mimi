Scope:

- Design the next implementation stage for a runtime Postgres adapter（运行时 Postgres 适配层）.
- Keep the adapter server-only and backed by Neon Postgres（关系型数据库）development / preview env vars.
- Preserve `person_id` filtering on every durable learning-data operation.
- Keep current browser `localStorage`（本地浏览器存储）runtime as the default fallback until the adapter is proven.
- Define a safe feature flag（功能开关）/ runtime mode boundary before any UI cutover.
- Define development / preview smoke tests for database-backed read/write paths.
- Document why Production（生产）database runtime remains disabled for now.

Non-Scope:

- No Production database env vars.
- No Production database migration.
- No Production data import.
- No formal Production release or promotion.
- No deletion of the current non-official Production deployment.
- No authentication（认证）or password isolation between trusted people.
- No public database write endpoints on the current Production alias.
- No local backup import into Neon.
- No embedding（向量嵌入）, FSRS（Free Spaced Repetition Scheduler，自由间隔重复调度算法）, AI generation, analytics（分析追踪）, email, notification, or 付费/扣款 feature.

Safety / Side Effects:

- Stage 5H is design-only unless separately confirmed for implementation.
- Any implementation stage that writes to Neon must remain development / preview only until a separate Production gate.
- Because the product intentionally has no user password model yet, runtime Postgres writes must not be exposed through an active public Production site.
- Server code must never expose `DATABASE_URL`, `POSTGRES_URL`, Neon credentials, or generated bypass tokens to client components.
- If a runtime mode is missing, invalid, or production-like, the app should fall back to local-only behavior or fail closed on write endpoints.
- The current non-official Production deployment from branch `V1` is a state-management risk and must remain documented until formal V1 release work.

Design Decision:

Stage 5H should not immediately switch the user-facing app from `localStorage` to Postgres. The safer next implementation is an adapter-first stage:

1. Add a server-only Postgres client module with lazy initialization.
2. Implement a Postgres repository that matches `DurableRepositoryPort`.
3. Add minimal development / preview API routes or server actions for adapter smoke tests.
4. Keep UI routes on `localStorage` by default.
5. Add explicit runtime mode selection only after the adapter passes tests.
6. Gate database write endpoints away from Production until an accepted access-boundary plan exists.

Proposed Implementation Shape:

- `src/lib/storage/postgres/client.ts`
  - Creates a lazy Neon `Pool`.
  - Reads only server-side env vars.
  - Rejects Production-like environments unless an explicit future Production gate exists.
- `src/lib/storage/postgres/mappers.ts`
  - Converts snake_case database rows to current TypeScript domain types.
  - Converts current domain inputs into database insert/update shapes.
- `src/lib/storage/postgres/repository.ts`
  - Implements `DurableRepositoryPort`.
  - Starts with `people`, `reviewSettings`, vocabulary list/add/update/archive/restore, import commit, review queue, and review record.
  - Uses explicit `personId` arguments and transactions for write operations.
- `src/lib/storage/runtime-mode.ts`
  - Defines accepted runtime modes such as `local` and `postgres-preview`.
  - Defaults to `local`.
  - Rejects accidental Production Postgres mode for now.
- Optional preview-only API routes:
  - `/api/storage/health`
  - `/api/storage/people`
  - `/api/storage/smoke`
  - These routes are for development / preview verification, not public Production use.

Adapter Rules:

- Every read/write query must include `person_id` when touching learning data.
- Mutations should use one transaction per logical operation.
- Review recording must write `review_events` and upsert / update `review_states` atomically.
- Import commit must insert the batch and accepted vocabulary items atomically.
- Archive / restore must enforce selected `person_id`.
- Duplicate detection must be person-scoped.
- Timestamps should be supplied from the caller and stored as `timestamptz`.
- Database UUIDs are canonical once data is in Postgres.

Runtime Boundary:

- Default app runtime remains `localStorage`.
- Development / preview can opt into Postgres after adapter tests.
- Production must not use Postgres runtime until:
  - formal V1 Production gate is accepted,
  - database env vars are intentionally scoped to Production,
  - access boundary is accepted,
  - backup/import/rollback behavior is documented,
  - Production smoke tests are planned.

Stop Conditions:

- Any query missing `person_id` on learning-data tables.
- Any server code exposing database env vars to client bundles.
- Any accidental Production env var dependency.
- Any deployment inspect result that is not Preview during adapter smoke.
- Any write endpoint reachable from Production without an accepted access boundary.
- Any count mismatch or partial transaction failure during future import work.

Exit Criteria For This Design Stage:

- Stage 5H design is documented.
- Stage 5G deployment facts are updated with the latest automatic Preview.
- No code runtime is changed.
- No database writes are performed.
- Governance validation passes.
